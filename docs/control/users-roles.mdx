Users & Access controls who can access a workspace and what actions they can perform. It is the first place to configure team access before teammates start building, deploying, or inspecting production systems.

## Why roles matter

Fast delivery requires shared access, but not every user needs the same permissions. Role-based access helps teams move quickly while limiting who can change production-sensitive settings.

Use roles to:

- Give developers access to build and deploy workflows
- Give stakeholders read-only visibility
- Keep workspace administration limited to owners
- Reduce accidental production changes
- Make access reviews easier

## Common roles

| Role | Typical access | Use for |
| --- | --- | --- |
| Admin | Full workspace management | Workspace owners and platform administrators |
| Developer | Build and deploy access | Engineers shipping application changes |
| Viewer | Read-only access | Product, QA, support, or leadership stakeholders |

## Invite workflow

<Steps>
  <Step title="Open workspace settings">
    Go to the workspace where the user should have access.
  </Step>

  <Step title="Invite the user">
    Enter the teammate's email address.
  </Step>

  <Step title="Assign a role">
    Choose the lowest role that gives the user the access they need.
  </Step>

  <Step title="Confirm access">
    Review the users list after the invite is accepted.
  </Step>
</Steps>

## What to review

Regularly check:

- Active users
- Email addresses
- Assigned roles
- Joined date
- Users who no longer need access
- Users with production-sensitive permissions

## Permission guidance

Use least-privilege access:

- Give Admin only to workspace owners.
- Give Developer to users who build or deploy applications.
- Give Viewer to users who only need logs, metrics, release history, or previews.

## Example access model

| Team member | Suggested role | Why |
| --- | --- | --- |
| Platform lead | Admin | Owns workspace settings and production-sensitive controls |
| Backend engineer | Developer | Builds features and deploys services |
| QA reviewer | Viewer | Reviews previews, logs, and release state |
| Product manager | Viewer | Needs visibility without write access |

## Best practices

- Review access before production launch.
- Remove users who leave the team.
- Keep production deployment permissions limited.
- Use Viewer access for stakeholders who do not need write permissions.
- Revisit roles after team or responsibility changes.
