Metrics turn application and delivery activity into measurable trends. Use them to understand whether the system is healthy and whether releases are improving or hurting performance.

![Revolte insights dashboard showing infrastructure and service-level metrics](/images/docs/doc-info-2.png)

## Why metrics matter

Logs explain individual events. Metrics show patterns across time. They help you see whether a release changed latency, whether memory usage is climbing, whether deployments are failing more often, or whether recovery time is improving.

## System metrics

System metrics can include:

- CPU usage
- Memory usage
- Network throughput
- Request latency
- Error rate
- Instance health

## Delivery metrics

Revolte can also surface delivery-focused metrics such as:

- Deployment frequency
- Lead time for changes
- Change failure rate
- Mean time to recovery

These help teams balance speed and reliability.

## DORA metrics

DORA metrics provide a standardized way to measure the performance of your engineering team's delivery process. Revolte captures these metrics natively across all environments to help you balance delivery speed with system stability.

## When to use metrics

Use metrics to:

- Confirm a deployment is healthy
- Detect regressions after release
- Understand long-term performance trends
- Compare environments
- Decide whether to roll back, scale, or optimize

## Metrics workflow

<Steps>
  <Step title="Select the application">
    Open the application and choose the environment or service you want to inspect.
  </Step>

  <Step title="Set the time range">
    Use a window that includes the deployment or incident timestamp.
  </Step>

  <Step title="Compare before and after">
    Look for changes in latency, error rate, CPU, memory, or throughput around the release.
  </Step>

  <Step title="Open logs for spikes">
    Use logs to investigate the exact cause behind abnormal metrics.
  </Step>

  <Step title="Choose an action">
    Roll back, scale, optimize, fix configuration, or continue monitoring.
  </Step>
</Steps>

## Reading metrics after deployment

After a release, check:

- Error rate
- Latency
- Resource usage
- Deployment success state
- Any trend that changed at the release timestamp

## Empty states

If no metrics appear yet, the application may not have received traffic or executed workloads. Generate traffic, wait for collection, then refresh the view.

## Best practices

- Always correlate metrics with deployment history.
- Use logs for exact failure details.
- Watch both performance and reliability.
- Track delivery metrics over time, not from a single release.
