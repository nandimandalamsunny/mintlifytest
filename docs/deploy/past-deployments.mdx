Past Deployments is the release ledger for an application. Use it to answer the operational questions that usually come up right after a release: what version is live, when it shipped, who triggered it, how long it took, and which earlier deployment is safe to restore.

![Past deployments table showing commit, commit message, deployment time, duration, initiator, status, and rollback action](/images/deployment/past-deployment.png)

## Why history matters

Past deployment history is more than a list of completed jobs. It is the audit trail for release decisions and the fastest way to reconstruct what changed in a running environment.

Use it when you need to:

- Confirm which commit is currently live
- Trace when a regression first appeared
- Compare release frequency and deployment duration
- Validate that a hotfix actually reached the target environment
- Identify a stable rollback candidate during an incident

## What the table shows

Each row represents one release attempt for the application. The table gives you both engineering context and operational context in one place.

| Column | What it tells you | Why it matters |
| --- | --- | --- |
| Commit | The code revision that was deployed | Lets you map runtime behavior back to source control |
| Commit Message | The merge or change summary associated with the deployment | Helps you understand the intent of the release without opening Git first |
| Deployment Time | When the deployment was executed | Useful when correlating incidents, alerts, or support reports |
| Duration | How long the deployment took | Helps surface unusually slow releases or infrastructure issues |
| Initiated By | The user or automation that triggered the release | Important for audits and incident review |
| Status | Whether the deployment succeeded, failed, is running, or was rolled back | Gives the current outcome at a glance |
| Rollback Action | A direct way to restore a previous stable version | Reduces decision time during production incidents |

## How to read the page

Start from the newest deployment and work backward.

<Steps>
  <Step title="Identify the current release">
    Look at the most recent successful row to confirm the latest version promoted into the environment.
  </Step>

  <Step title="Use the commit message for context">
    The message usually reveals whether the release was a feature merge, a hotfix, or a branch promotion.
  </Step>

  <Step title="Correlate timing with incidents">
    Compare deployment time with the first error spike, support report, or monitoring alert.
  </Step>

  <Step title="Check deployment duration">
    Longer-than-usual durations can point to build issues, infrastructure contention, or rollout instability.
  </Step>

  <Step title="Choose the next action">
    Decide whether to inspect logs, compare against an earlier release, or restore a known good version.
  </Step>
</Steps>

## When to use it

Use Past Deployments for:

- Daily release review
- Incident response
- Post-deployment verification
- Rollback decisions
- Change audits
- Comparing deployment duration trends over time

## Investigation workflow

When a deployment may be connected to a runtime issue, this page should usually be the first checkpoint after alerts or logs.

<Steps>
  <Step title="Find the suspected deployment window">
    Use Deployment Time to narrow the release that most likely introduced the problem.
  </Step>

  <Step title="Inspect the release intent">
    Read the commit message and commit identifier to understand what changed and which code revision to investigate.
  </Step>

  <Step title="Open supporting signals">
    Cross-check the same time window in [Activity Timeline](/docs/deploy/deployment-activity), [Logs](/docs/observe/logs), and [Metrics](/docs/observe/metrics).
  </Step>

  <Step title="Decide whether the issue is release-related">
    If the failure lines up with the deployment and the prior version was healthy, move toward rollback or a fast follow-up fix.
  </Step>
</Steps>

## Example: deciding whether to roll back

Imagine production errors rise at 03:55 pm and the latest successful deployment completed at 03:50 pm. In Past Deployments you can immediately:

- Confirm which commit shipped at 03:50 pm
- See whether the release was a feature merge or a branch promotion
- Compare it with the previous stable deployment
- Pick the earlier successful row if rollback is the safest path

## Rollback workflow

Rollback should restore a known stable version and leave an auditable record.

<Steps>
  <Step title="Find the last stable deployment">
    Look for the most recent release that completed successfully before the incident began.
  </Step>

  <Step title="Review the failed release">
    Check activity and logs so you understand why rollback is needed.
  </Step>

  <Step title="Start the revert action">
    Use the stable deployment row as the rollback target.
  </Step>

  <Step title="Confirm the target version">
    Verify the commit, environment, and expected application state before proceeding.
  </Step>

  <Step title="Verify after rollback">
    Confirm the restored version is healthy using logs and metrics.
  </Step>
</Steps>

> ✅ **Recommended practice**  
> Roll back to the most recent version you trust, not simply the version right before the current one. A recent deployment can still be unhealthy even if it completed successfully.

## Status meanings

| Status | Meaning |
| --- | --- |
| In progress | Deployment is still running |
| Successful | Deployment completed |
| Failed | Deployment did not complete |
| Rolled back | A previous version was restored |

## Release review checklist

Before you treat a deployment as safe, verify:

- The expected commit is present in the target environment
- The deployment completed with a healthy status
- The deployment duration is within a normal range
- The correct user or automation triggered the release
- Logs and metrics look normal after the deployment time

## Rollback considerations

Rollback restores an application version, but it may not undo every external change. Review:

- Environment variables changed after the target deployment
- Database migrations or data changes
- External service configuration
- Feature flags
- Secrets rotated after the original release

## Best practices

- Treat Past Deployments as the canonical release timeline for the environment.
- Revert only to deployments you trust.
- Review activity before rollback.
- Confirm environment variables still match the restored version.
- Validate logs and metrics after rollback.
- Treat rollback as a new deployment event, not a hidden state change.
- Use commit identifiers here to coordinate conversations between engineering, QA, and support.
