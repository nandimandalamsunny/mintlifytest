Activity Timeline is the timeline view for a release. It shows what happened during deployment, when each event occurred, and whether the event was triggered by a user or system action.

## Why activity exists

Raw logs are useful when you need detail, but they are too noisy for a quick release status check. Activity Timeline gives you the ordered release story: started, built, provisioned, deployed, failed, rolled back, or completed.

## What activity shows

Activity entries can include:

- Deployment started
- Build artifact created
- Infrastructure provisioned
- Environment variables applied
- Deployment completed
- Deployment failed
- Rollback started
- Rollback completed

## When to use it

Use Activity Timeline when you need to:

- Confirm a release progressed as expected
- Audit who or what triggered a deployment
- Understand the order of deployment events
- Quickly check status without reading raw logs
- Correlate deployments with runtime issues

## Activity vs logs vs history

| View | Answers |
| --- | --- |
| Activity Timeline | What happened, and in what order? |
| Logs | How did each step execute? |
| Past Deployments | What versions were released over time? |

## Debugging workflow

<Steps>
  <Step title="Open the deployment record">
    Start from the deployment that failed, slowed down, or introduced an issue.
  </Step>

  <Step title="Read the activity timeline">
    Move from the first event to the latest event and identify the first failed or delayed stage.
  </Step>

  <Step title="Open logs for the stage">
    Use logs when you need command-level or runtime detail.
  </Step>

  <Step title="Compare with metrics">
    After a completed release, use metrics to confirm whether the system stayed healthy.
  </Step>
</Steps>

## Example scenario

If production latency rises after a release, use Activity Timeline to identify the exact deployment time, then compare metrics before and after that timestamp. If the issue aligns with the release, open logs for the deployed application or roll back from Past Deployments.

## Best practices

- Check activity before rollback decisions.
- Use timestamps to match releases with incidents.
- Compare actor context with expected release ownership.
- Move to logs when you need command-level detail.
