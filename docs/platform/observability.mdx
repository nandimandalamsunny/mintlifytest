Observability in Revolte is designed to answer the practical questions that come after a release: is the application healthy, did the new change introduce a regression, and where should the investigation start.

## Connect Signals to Releases

When observability lives outside the delivery workflow, teams lose time reconstructing what changed and when.

Revolte keeps release context attached to runtime signals so teams can move from release event to diagnosis faster.

## Observability Signals

| Signal | What it helps you understand |
| --- | --- |
| Logs | Specific runtime behavior, errors, and execution detail |
| Metrics | Aggregated health, performance, and regression signals |
| Activity | Release timing and deployment lifecycle context |
| Deployment history | Which version changed the running system and when |

## How Observability Fits Delivery

<Steps>
  <Step title="A change is released">
    A deployment introduces a new version into an environment.
  </Step>
  <Step title="Signals become the verification layer">
    Teams use logs, metrics, and activity to confirm whether the release is healthy.
  </Step>
  <Step title="Investigation narrows quickly">
    If behavior regresses, teams can move from deployment timing to logs or metrics without leaving the platform context.
  </Step>
  <Step title="Next action becomes clearer">
    The team can decide whether to continue, fix forward, or roll back based on evidence instead of guesswork.
  </Step>
</Steps>

## Common Use Cases

Use observability for:

- Post-deployment verification
- Incident triage
- Regression investigation
- Comparing behavior before and after a release

## Choosing Logs vs Metrics

| Start with | Best when you need |
| --- | --- |
| Logs | Concrete error detail, request behavior, or execution evidence |
| Metrics | Trend changes, latency shifts, error spikes, or health comparisons |

## Recommended Practices

- Check observability immediately after important releases.
- Use deployment timing as the anchor for investigation.
- Start broad with metrics, then go specific with logs when needed.
- Compare signals against the last known healthy deployment.
