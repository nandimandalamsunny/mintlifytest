---
title: "Preview Deployments"
---

Preview Deployments give teams a running version of a change before it is merged into a shared environment. They reduce review friction by turning code review into product review.

## Validate Before Merge

Previews are useful when a diff alone is not enough to validate a change.

Use them to:

- Review UI behavior before merge
- Validate branch-specific runtime changes
- Share a working environment with QA or stakeholders
- Catch integration issues earlier in the delivery flow

## What A Preview Contains

A preview deployment typically provides:

- A branch-specific running version of the application
- Environment-scoped runtime configuration
- A review surface tied to a specific code change
- Logs and deployment state for the preview release

## Preview Lifecycle

<Steps>
  <Step title="A change is opened for review">
    A pull request or review branch becomes the candidate for preview validation.
  </Step>
  <Step title="Revolte creates the preview deployment">
    The platform provisions a temporary running instance for that version of the application.
  </Step>
  <Step title="Teams review the change in context">
    Engineers, QA, and stakeholders can inspect actual behavior instead of relying only on screenshots or diffs.
  </Step>
  <Step title="The preview is replaced or discarded">
    Once the change is merged, updated, or closed, the preview lifecycle follows the release workflow.
  </Step>
</Steps>

## Best Use Cases

Preview Deployments are especially valuable for:

- Frontend changes
- Cross-service integration checks
- Configuration-sensitive features
- Product review before merge

## Preview Review Flow

<Steps>
  <Step title="Open the preview">
    Start with the branch or pull request under review.
  </Step>
  <Step title="Validate expected behavior">
    Check the user flow, API behavior, or runtime integration you care about.
  </Step>
  <Step title="Review supporting signals">
    Inspect deployment status, logs, or activity if something looks wrong.
  </Step>
  <Step title="Approve or iterate">
    Merge when the preview is healthy, or update the branch and repeat.
  </Step>
</Steps>

## Recommended Practices

- Use previews for behavior review, not only visual confirmation.
- Keep environment-specific assumptions explicit when validating previews.
- Check logs if a preview behaves differently from local development.
- Treat preview success as a confidence signal, not the only release gate.
