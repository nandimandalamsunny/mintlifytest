Environments are one of the core platform boundaries in Revolte. They separate where code runs, how configuration is applied, and which version of an application is considered active for a given stage.

## Isolate Environments Securely

Without clear environment boundaries, teams end up mixing preview, QA, staging, and production concerns in ways that create deployment risk.

Revolte uses environment isolation to help teams:

- Validate changes safely before production
- Keep runtime configuration scoped to the correct stage
- Reduce accidental cross-environment leakage
- Promote code through a predictable release model

## Isolation Model

| Area | How isolation helps |
| --- | --- |
| Deployments | Each environment tracks its own release history and active version |
| Configuration | Variables and secrets can be scoped to the environment where they are needed |
| Validation flow | Preview, QA, staging, and production can serve different review purposes |
| Operational impact | Testing or rollback decisions can be made per environment instead of globally |

## Common Environment Stages

Most teams use some variation of this structure:

| Environment | Purpose |
| --- | --- |
| Preview | Validate branch or pull request changes before merge |
| QA | Test functional behavior in a shared verification stage |
| Staging | Rehearse production-like releases before final rollout |
| Production | Serve live application traffic |

## Environment Flow

<Steps>
  <Step title="Define release targets">
    Choose which environments your application needs based on review and release requirements.
  </Step>
  <Step title="Map delivery flow">
    Connect branch or deployment triggers to the correct target environment.
  </Step>
  <Step title="Scope configuration">
    Apply variables, secrets, and services only where they are required.
  </Step>
  <Step title="Promote with intent">
    Move code through environments based on review confidence and release policy.
  </Step>
</Steps>

## When To Increase Isolation

Increase environment discipline when:

- Production changes need stronger review gates
- Different teams share the same platform
- Runtime configuration differs by stage
- Rollback decisions must be auditable and low risk

## Recommended Practices

- Keep production configuration scoped tightly.
- Use preview environments for early review instead of testing directly in shared stages.
- Promote changes through environments intentionally, not by guesswork.
- Review environment variables and secrets per stage before release.
